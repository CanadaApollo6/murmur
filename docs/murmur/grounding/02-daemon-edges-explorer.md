# Explorer findings: Infinity daemon and edges

Source: Muse Wonder Full explorer, read-only pass over upstream Infinity at commit 1abc6fc.

### Components Found

All paths are under `` unless noted.

**Daemon process and session management**

- `run_daemon(announce_ready)` — [crates/infinity-daemon/src/lib.rs](../../../crates/infinity-daemon/src/lib.rs:44). Binds the Unix socket and WebSocket listener, builds the session manager, prints `DAEMON_READY_LINE` when supervised, and on SIGINT/SIGTERM stops all RAP servers via `rap_manager.shutdown_all()`.
- `launch_session_manager(state_dir)` — [crates/infinity-daemon/src/lib.rs](../../../crates/infinity-daemon/src/lib.rs:32). Shared startup for daemon mode and the CLI's direct mode: binds `RapCallbackBridge`, constructs `SessionManager` with its callback URL, then starts callback serving.
- Daemon entry points — [crates/infinity-daemon/src/main.rs](../../../crates/infinity-daemon/src/main.rs:3) calls `run_daemon(false)`; the shipped path is the `infinity` CLI binary's `daemon` subcommand calling `run_daemon(true)` in [crates/infinity-agent-cli/src/main.rs](../../../crates/infinity-agent-cli/src/main.rs:189). Both run `#[tokio::main(flavor = "current_thread")]` inside a `LocalSet`.
- `SessionManager` — [crates/infinity-daemon/src/session/mod.rs](../../../crates/infinity-daemon/src/session/mod.rs:77). Owns one daemon-lifetime agent system, the `ModelCatalog`, spawned provider `Child` handles, `SessionRapManager`, subscriber map, broadcast clients, and optional `RemoteDaemons`. `SharedSessionManager = Rc<Mutex<SessionManager>>` — deliberately `!Send`, single-threaded.
- `SessionManager::new` / `with_providers` — [crates/infinity-daemon/src/session/mod.rs](../../../crates/infinity-daemon/src/session/mod.rs:116). `new` spawns providers from `~/.infinity/providers.json`; `with_providers` accepts in-process `Vec<(String, Arc<dyn ModelProvider>)>` (tests use the mock this way). It builds the agent system with `AgentSystemBuilder::new_local(...).callback_url(...).thread_config(rap_manager).with_tokio_sleep_tools().build_local()` and starts it via `start_with_observer(make_observer)`.
- Session activity watcher (inside `with_providers`) — [crates/infinity-daemon/src/session/mod.rs](../../../crates/infinity-daemon/src/session/mod.rs:297). Consumes `ThreadLifecycleEvent::{Live,Idle}` plus idle pings; `evaluate_session_idle` stops a session's RAP servers only when no thread is live/subscribed and no keep-alive client remains.
- `SessionStore` / `SessionEntry` — [crates/infinity-daemon/src/session_store.rs](../../../crates/infinity-daemon/src/session_store.rs:38). Persists `~/.infinity/sessions.json`: per-root-thread `cwd`, `shut_down`, `idle`, `archived`; `status()` maps these plus pending choices to `infinity_protocol::SessionStatus`.
- `PersistentConversationStore` / `PersistentStateStore` — [crates/infinity-daemon/src/memory_store.rs](../../../crates/infinity-daemon/src/memory_store.rs:50). Wrap core's in-memory stores with per-thread JSON files under `~/.infinity/threads/` (`{id}.json`, `{id}.meta.json`, `{id}.views.json`) and daemon extras (`ThreadExtras`: title, children, token totals, `selected_model: ModelRef` via `get_thread_model`/`set_thread_model`).

**Client wire protocol (Infinity's own, not ACP)**

- `ClientMessage` / `DaemonMessage` — [crates/infinity-protocol/src/lib.rs](../../../crates/infinity-protocol/src/lib.rs:230). Client→daemon: `CreateSession{cwd,location,model,keeps_session_alive}`, `Connect`, `UserInput`, `Disconnect`, `SoftDetach`, `ShutdownSession`, `ArchiveSession`, `SwitchModel`, `UserChoiceAnswered`, `TriggerCompaction`, `RequestMigrate`, daemon-to-daemon `Emigrate`/`EmigrateDone`/`ImportSession`/`BootRapServers`, `ListDirectory`. Daemon→client: `Welcome`, `Connected`, `Replay{history,pending_choices,views,in_progress}`, streaming `TextChunk`/`ThinkingChunk`/`ToolCall`/`ToolResult{segments}`/`ResponseDone`, `SubscriptionEvent`, `UserChoiceRequired`, `ViewUpdate`, `SessionsUpdated`, `ModelSwitched`, migration replies.
- `ThreadRef` — [crates/infinity-protocol/src/lib.rs](../../../crates/infinity-protocol/src/lib.rs:29). Session = root thread's ref; serializes as `"{id}"` locally or `"{remote}/{id}"` remotely. `socket_path()`/`pid_path()`/`state_dir()` fix `~/.infinity/daemon.sock|pid`; `length_delimited_codec()` caps frames at 256 MiB.
- `handle_client` — [crates/infinity-daemon/src/client_handler.rs](../../../crates/infinity-daemon/src/client_handler.rs:236). Unix-socket framing (length-delimited JSON) bridged to mpsc channels.
- `handle_client_channels` — [crates/infinity-daemon/src/client_handler.rs](../../../crates/infinity-daemon/src/client_handler.rs:290). Transport-agnostic core handler: sends `Welcome` first, then dispatches every `ClientMessage`; also used directly over in-memory channels in CLI direct mode. `UserInput` becomes `InputMessage{User(UserContent::text), group_id}` via `SessionManager::send_input`; `UserChoiceAnswered` looks up `state_store().pending_choice(...)` and HTTP-POSTs `{id, selected}` to the tool's `response_url`.
- `ws_handler::serve` / `run_ws_loop` — [crates/infinity-daemon/src/ws_handler.rs](../../../crates/infinity-daemon/src/ws_handler.rs:23). Hyper HTTP server: WebSocket upgrades carry the identical `ClientMessage`/`DaemonMessage` JSON as text frames into `handle_client_channels`; other paths serve embedded web assets with SPA fallback.
- `DaemonObserver` — [crates/infinity-daemon/src/session/observer.rs](../../../crates/infinity-daemon/src/session/observer.rs:91). Implements core's `ThreadObserver`: `on_event` persists token/time state then broadcasts `agent_event_to_daemon(...)` ([session/display.rs](../../../crates/infinity-daemon/src/session/display.rs:7)); `on_subscribe` sends `Replay` built from `history_message_to_daemon` plus in-flight thinking text, pending choices, and persisted views. Children inherit their parent's subscriber list in the `make_observer` factory ([session/mod.rs](../../../crates/infinity-daemon/src/session/mod.rs:248)).

**Remotes and migration (daemon-as-client)**

- `RemoteDaemons` / `control_worker` — [crates/infinity-daemon/src/remote.rs](../../../crates/infinity-daemon/src/remote.rs:49). Per `~/.infinity/remotes.json` entry (`RemoteConfig{name, ssh_args}`), an SSH `-L` tunnel forwards the remote `~/.infinity/daemon.sock` to a local temp socket; a control connection mirrors remote `Welcome`/`SessionsUpdated` with `ThreadRef::prefixed` IDs. `open_raw_connection`/`connect_remote_session` open further connections over the same tunnel. `client_handler.rs` then proxies per-client traffic with `prefix_daemon_message`/`strip_client_message`.
- `orchestrate_migration` / `handle_emigrate` — `crates/infinity-daemon/src/migrate.rs` (grep-inspected). Boots destination RAP servers (`BootRapServers`), SSH-forwards/reverse-forwards ports for servers whose manifest sets `needsMigration`, calls each source server's `POST /migrate`, transfers `serialize_session` output via `Emigrate`/`ImportSession`, then `EmigrateDone` archives the source.

**Model providers (daemon side)**

- `ProvidersConfig` / `ProviderConfig{command, crate_name, git, path}` — [crates/infinity-daemon/src/models.rs](../../../crates/infinity-daemon/src/models.rs:33). Ordered map from `~/.infinity/providers.json` ([config::providers_config_path](../../../crates/infinity-daemon/src/config.rs:12)); document order is significant — first model of first provider is the global default. No implicit default: a missing file is a startup error (`load_providers_config`).
- `spawn_provider` / `spawn_configured_providers` — [crates/infinity-daemon/src/models.rs](../../../crates/infinity-daemon/src/models.rs:198). Spawns `command` argv with null stdin, piped stdout/stderr, `kill_on_drop(true)`; reads the first stdout line as the Unix socket path (30 s `PROVIDER_STARTUP_TIMEOUT`), forwards all later output to the daemon log, wraps the socket in `RemoteModelProvider`. Children are held in `SessionManager::_provider_processes` for the daemon's lifetime — no health check or respawn anywhere.
- `ModelCatalog` — [crates/infinity-daemon/src/models.rs](../../../crates/infinity-daemon/src/models.rs:276). Calls `list_models()` once per provider at startup; `resolve(selected)` falls back to the default for stale selections. `CatalogModelSource: ModelSource::resolve` re-reads each thread's persisted `ModelRef` every completion round, which is the entire model-switching mechanism (`SessionManager::switch_model` just persists + broadcasts `ModelSwitched`).

**Provider protocol (process/wire side)**

- `ModelProvider` trait — [crates/infinity-provider-protocol/src/lib.rs](../../../crates/infinity-provider-protocol/src/lib.rs:68). Exactly two methods: `list_models() -> Vec<ModelEntry{model_id, display_name, context_window, max_output_tokens, supports_image_input}>` and `invoke_model(model_id, CompletionRequest) -> ModelStream`. `CompletionModel` + `SingleModelProvider` adapt single-model impls.
- `CompletionRequest` / `StreamChunk` / `ErrorClass` — [crates/infinity-provider-protocol/src/completion.rs](../../../crates/infinity-provider-protocol/src/completion.rs:16). Request = `preamble + chat_history: Vec<Message> + tools: Vec<ToolDefinition> + max_tokens + additional_params`; stream items are `Text | ToolCall | ToolCallDelta | Reasoning | ReasoningDelta | Final{usage}`; errors must be provider-classified `Transient|Throttled|ContextOverflow|Fatal` because core's `run_completion` in `crates/infinity-agent-core/src/event_processor.rs` retries/shrinks/aborts purely on `e.class()` (grep-inspected ~line 1526). Message types in [message.rs](../../../crates/infinity-provider-protocol/src/message.rs:17) are byte-compatible with rig 0.31 because persisted histories embed them.
- `serve_provider` / `RemoteModelProvider` / `ProviderRequest` / `ProviderResponse` — [crates/infinity-provider-protocol/src/remote.rs](../../../crates/infinity-provider-protocol/src/remote.rs:149). Newline-delimited JSON over a temp-dir Unix socket, one request per connection: `ListModels → Models|Error`; `InvokeModel → InvokeStarted, Chunk(...)*, StreamEnd` (or single `Error`); `WireError` preserves `ErrorClass` across the process boundary. Feature-gated (`remote`, unix-only).
- Reference provider binary — [crates/infinity-provider-bedrock/src/main.rs](../../../crates/infinity-provider-bedrock/src/main.rs:16) is 34 lines: build provider, `serve_provider`, `println!(socket_path)`, await forever; logs to stderr. `BedrockProvider: ModelProvider` ([lib.rs](../../../crates/infinity-provider-bedrock/src/lib.rs:365)) shows the real work: `prepare_request` + [convert.rs](../../../crates/infinity-provider-bedrock/src/convert.rs:73) (`messages`, `tool_config`) ≈433 lines and [stream.rs](../../../crates/infinity-provider-bedrock/src/stream.rs:65) `convert_stream` ≈254 lines adapt the backend stream to `StreamChunk`s, accumulating tool-call JSON itself.
- `RigCompletionModel` — [crates/infinity-provider-rig/src/lib.rs](../../../crates/infinity-provider-rig/src/lib.rs:51). Optional bridge: wraps any `rig::completion::CompletionModel`, `.into_provider(ModelEntry)` yields a `ModelProvider`; all conversions already exist in [convert.rs](../../../crates/infinity-provider-rig/src/convert.rs:24) (`request_to_rig`, `chunk_from_rig`, `error_from_rig` with message-string classification for OpenAI-compatible backends). Not used by the daemon today; docs describe serving rig's OpenAI/Anthropic/Gemini backends this way ([docs/docs/infinity-runtime/model-providers.md](../../../docs/docs/infinity-runtime/model-providers.md:72)).
- `mock_model()` — [crates/infinity-provider-protocol/src/mock.rs](../../../crates/infinity-provider-protocol/src/mock.rs:123). Channel-driven `CompletionModel` used to test the whole daemon without an LLM.

**RAP servers, callbacks, MCP (daemon side)**

- `SessionRapManager: ThreadConfigSource` — [crates/infinity-daemon/src/rap_servers.rs](../../../crates/infinity-daemon/src/rap_servers.rs:432). Lazily resolves a session's toolset on its first thread step (`get_or_init`): reads merged config, boots servers, fetches manifests, builds one `ManagedRapTool` per `ToolDef`, plus the built-in `set_title` tool and a cwd system-prompt suffix. `shutdown_session` keeps the cached toolset; `evict_session` drops it.
- `ManagedRapServer` / `ServerSpec` — [crates/infinity-daemon/src/rap_servers.rs](../../../crates/infinity-daemon/src/rap_servers.rs:53). Four spec kinds mirror `ToolSetConfig` ([infinity-agent-core/src/tools/config.rs](../../../crates/infinity-agent-core/src/tools/config.rs:7)): `Command`, `Mcp`, `HttpMcp`, `External{url}`. `ensure_up()` boots if down and caches the manifest; `invoke_endpoint()` reboots transparently; `shutdown()` SIGINTs only command servers' process groups — MCP proxies and external servers are never stopped.
- `spawn_rap_server` — [crates/infinity-daemon/src/rap_servers.rs](../../../crates/infinity-daemon/src/rap_servers.rs:324). Runs `sh -c <command>` with `RAP_EMBEDDED=1`, cwd `{cwd}/.infinity`, own process group, stderr discarded; first stdout line must parse as `CommandServerReady{port}`. Config comes from `load_merged_rap_config` ([config.rs](../../../crates/infinity-daemon/src/config.rs:28)): `{cwd}/.infinity/rap.json` merged over `~/.infinity/rap.json`, deduped by entry `id`.
- `ManagedRapTool: Tool` — [crates/infinity-daemon/src/rap_servers.rs](../../../crates/infinity-daemon/src/rap_servers.rs:377). `execute()` resolves the (possibly rebooted) endpoint then delegates to `invoke_rap_tool` ([infinity-agent-core/src/tools/rap_tool.rs](../../../crates/infinity-agent-core/src/tools/rap_tool.rs:72)), which POSTs one `RapInvocation{operation, arguments, id, call_id, callback_url, group_id, user_id, thread_ancestors}` and returns immediately — results arrive later by callback. Non-2xx synthesizes an error tool result; transport failure returns `Err`.
- `rap_callback::serve_callbacks` — [crates/infinity-daemon/src/rap_callback.rs](../../../crates/infinity-daemon/src/rap_callback.rs:21). Only splits the bridge output: agent inputs go straight into `session_manager.input_sender()`; `view_update`s go to `SessionManager::handle_view_update` (persist via `set_view`, broadcast `DaemonMessage::ViewUpdate`, never enter history).
- `RapCallbackBridge` / `prepare_callback` — [crates/infinity-rap-bridge/src/lib.rs](../../../crates/infinity-rap-bridge/src/lib.rs:42). Binds `127.0.0.1:0` HTTP listener; assigns dedup IDs (`rap-tool-result-{id}`, etc.; subscription events get fresh UUIDs since RAP has no per-event ID); `convert_callback` ([callback.rs](../../../crates/infinity-rap-bridge/src/callback.rs:26)) maps each `RapCallback` to an `InputMessage` (subscription events become `SyntheticKind::SubscriptionEvent{associative, final}`).
- `mcp_proxy::start_mcp_proxy` / `start_http_mcp_proxy` — [crates/infinity-daemon/src/mcp_proxy.rs](../../../crates/infinity-daemon/src/mcp_proxy.rs:101). In-process HTTP server presenting an MCP server as a RAP toolset: `GET /.well-known/rap-toolset` from `McpClient::describe_toolset()`, `POST /invoke` → `McpClient::dispatch(...)` → POSTs `RapCallback::ToolResult` (never `subscription`) to the invocation's callback URL.
- `McpClient` — `crates/infinity-mcp-bridge/src/lib.rs` (excerpt-inspected). Lazily connects one stdio child (`StdioMcpTransport`, newline JSON-RPC) or Streamable-HTTP session and collapses the whole MCP server into two meta-tools, `{name}_list_tools` and `{name}_invoke_tool` (`tool_definitions`, `dispatch`); `McpToolSet` exposes the same client directly as core `Tool`s for non-daemon embeddings.

### Flow

**Daemon startup (single machine)**

1. `infinity` (no subcommand) → `daemon_client::run_with_daemon` → `ensure_daemon_running` ([daemon_client.rs](../../../crates/infinity-agent-cli/src/daemon_client.rs:132)): try `~/.infinity/daemon.sock`, else `launch_daemon` spawns `current_exe daemon` and waits for the ready line.
2. `run_daemon(true)` ([infinity-daemon/src/lib.rs](../../../crates/infinity-daemon/src/lib.rs:44)): create `~/.infinity`, open `daemon.log`, delete stale socket, bind `UnixListener`, write PID file.
3. `launch_session_manager` → `RapCallbackBridge::bind()` (TCP `127.0.0.1:0`, URL like `http://127.0.0.1:{port}`) → `SessionManager::new` → `load_providers_config` + `spawn_configured_providers` (each provider process prints its socket path) → `ModelCatalog::new` (`ListModels` per provider) → load `sessions.json`, build persistent stores → `AgentSystemBuilder::new_local(...).build_local()` → `start_with_observer` spawns `route_loop` → `rap_callback::serve_callbacks` starts the callback HTTP server into `ChannelSender`.
4. `remote::load_remotes_config` → `SessionManager::init_remotes` spawns one SSH-tunnel `control_worker` per remote. Bind WebSocket TCP `127.0.0.1:8080` (`INFINITY_WS_PORT`/`INFINITY_WS_BIND` overrides). Print `DAEMON_READY_LINE`. Accept loops `spawn_local` per connection.

**Client attach and a normal turn**

5. Client connects (Unix framing or WS text frames) → `handle_client_channels` immediately sends `DaemonMessage::Welcome{sessions, available_models, default_model_name, remotes}` and registers the connection for `SessionsUpdated` broadcasts (`list_sessions(Some(tx))`).
6. `CreateSession{cwd, model}` → `SessionManager::create_session` ([session/mod.rs](../../../crates/infinity-daemon/src/session/mod.rs:449)): mint root thread ID, persist `SessionEntry{cwd}`, `ensure_root_thread`, `set_thread_model`, emit `Connected{root_thread_id, model_name, context_window, provider_id}`; then `attach_client` → `SubscribeHandle::subscribe` → router spawns a driver → `DaemonObserver::on_subscribe` (no replay for fresh sessions). For `Connect`, `resume_session` + `attach_client(wants_replay=true)` yields `Connected` then `Replay{history, pending_choices, views, in_progress}`. No model or tools are touched yet.
7. `UserInput{thread_id, text}` → `SessionManager::send_input` → `ChannelSender::send_to_input_queue(InputMessage{User(Text), group_id=thread})` → `route_loop` spawns/reuses `drive_thread` (lifecycle `Live` → watcher clears `idle`/`shut_down`).
8. Driver resolves per-thread config: `SessionRapManager::resolve` → `get_or_init(session_id)` on first use boots each `ManagedRapServer::ensure_up()` (`spawn_rap_server` or MCP proxy or external URL), `fetch_manifest` (`GET /.well-known/rap-toolset`), builds `ManagedRapTool`s + `set_title` + cwd prompt. `CatalogModelSource::resolve` picks the thread's provider/model.
9. Core `run_completion` builds `CompletionRequest{preamble: default_prompt + thread IDs + extra_system_prompt, chat_history, tools, max_tokens: None, additional_params: None}` — note generation parameters are always provider-chosen — and calls `provider.invoke_model`. For the daemon that is `RemoteModelProvider::invoke_model`: new Unix connection, one `InvokeModel` JSON line, expect `InvokeStarted`, then map each `Chunk` line back to `StreamChunk` until `StreamEnd`. Provider process: `handle_invoke` → real `ModelProvider::invoke_model` (e.g. Bedrock `converse_stream` → `convert_stream`).
10. Stream chunks become core `AgentEvent`s → `DaemonObserver::on_event` → `agent_event_to_daemon` → `DaemonMessage::{ThinkingChunk, TextChunk, ToolCall, ResponseDone{token_usage}}` fanned out to thread subscribers (children inherit parent subscribers, so a root-attached TUI/WS client sees subthreads, tagged with their `thread_id`).

**Tool execution and callback re-entry (the RAP loop)**

11. Model emits a tool call → core dispatches `ManagedRapTool::execute` → `server.invoke_endpoint()` (transparent reboot) → `invoke_rap_tool` POSTs `RapInvocation{operation, arguments, id: tool_call_id, call_id, callback_url: <bridge URL>, group_id: thread_id, thread_ancestors}` to the manifest `endpoint` and returns. The thread now waits; nothing blocks.
12. RAP server (e.g. sandbox `invoke_handler`) returns HTTP 200 at once, works in a spawned task, then POSTs `RapCallback::ToolResult{group_id, id, text|content, display_as, subscription}` to `callback_url`.
13. `rap-client` callback server → `RapCallbackBridge::serve_into` → `prepare_callback` (dedup `rap-tool-result-{id}`) → `convert_callback` → `ChannelSender::send_to_input_queue` → `route_loop` admission (thread must exist and not be stopped, else dropped) → driver respawns if idle → tool result appended to history → next completion round (step 9). Synchronous built-in tools (`spawn_thread`, `cancel_subscription`, sleep) bypass HTTP via `Tool::execute_synchronous` / direct `send_to_input_queue`.

**Subscriptions, choices, views**

14. Subscription start: a tool result with `subscription=true` (sandbox long commands, `subscribe_github_events`) makes core record the tool-call ID via `StateStore::add_active_subscription` (in `event_processor.rs` prepare path, read at offset 1040). The daemon watcher treats a thread with active subscriptions as still active even after its driver idles, so its RAP servers stay up.
15. Each later `RapCallback::SubscriptionEvent{group_id, tool_call_id, text, associative, final}` re-enters exactly like step 13 but as a synthetic input. In core's prepare logic: if `associative` (sandbox streaming) the event is inlined into the subscribing thread as a synthetic `receive_event__injected` tool call/result pair; if not (GitHub poller), an ephemeral child thread is spawned (`spawn_thread(..., is_subscription=true, InheritUpTo(safe_spawn_point))`), seeded with the event, and expected to `report_to_parent` + `close_thread`. `final=true` removes the subscription. Deferrable synthetics (subscription events, thread reports, parent messages) are held in `InMemoryDeferQueue` while a non-passive tool call is pending (`system/defer.rs`, excerpt-inspected) to avoid interrupting it. `cancel_subscription` (model-invoked) → `RapNotifier::notify_tool_cancelled` (`POST /cancel_tool_call` to all up servers) + remove from store.
16. `RapCallback::UserChoice{response_url}` → stored as a pending choice → `DaemonMessage::UserChoiceRequired` to clients → client answers `UserChoiceAnswered{choice_id, selected}` → daemon POSTs `{id, selected}` to `response_url` → the tool's `/user_choice_response` handler unblocks its oneshot and continues (sandbox permission flow). `RapCallback::OAuth` similarly surfaces as `OAuthRequired{auth_url}`. `RapCallback::ViewUpdate` is the only callback diverted in `rap_callback.rs`: persisted per thread and broadcast as `ViewUpdate`, replayed from `Replay.views`, never shown to the model.

**Idle, shutdown, restart**

17. Driver exits → lifecycle `Idle` → watcher: subscribed threads stay "active"; otherwise `evaluate_session_idle` marks the session idle and, absent keep-alive subscribers, `SessionRapManager::shutdown_session` SIGINTs command RAP servers (toolset cache retained). `ShutdownSession` → `cleanup_session`: clear pending choices, `evict_session` (stop + drop toolset), mark `shut_down` — later RAP callbacks are dropped by the router, later user text revives the session and lazily reboots servers. Daemon exit kills provider children (`kill_on_drop`) and calls `shutdown_all`; thread histories are already durable in `~/.infinity/threads/*.json`, so restart is just lazy reload.

**Remote sessions** reuse everything: `CreateSession{location: Some(name)}` or `Connect` with a remote `ThreadRef` makes `client_handler` open a raw daemon-protocol connection through the SSH Unix-socket tunnel and proxy messages with ID prefixing/stripping.

**ACP server flow** (`infinity acp`, stdio JSON-RPC)

18. Exactly these ACP requests are handled in [acp_server.rs](../../../crates/infinity-agent-cli/src/acp_server.rs:120): `initialize` → `InitializeResponse{protocol V1, agent_capabilities: load_session=true + session list, agent_info}`; `session/list` → daemon sessions (non-archived) mapped through persisted ACP↔daemon ID mappings (`.infinity/acp-sessions.json` in the server's cwd); `session/new` → returns a fresh UUID and only records `cwd` in `lazy_sessions` (no daemon session yet); `session/load` → spawns `run_session_connection(SessionStart::Load)` sending daemon `Connect`, responds after `Connected`, forwards daemon `Replay` once as notifications; `session/prompt` → concatenates **text** `ContentBlock`s only, then either forwards to the live per-session task as daemon `UserInput`, materializes a lazy session via daemon `CreateSession`, or connects-and-prompts an unloaded one; `session/set_model` → **stub: ignores the request and returns empty success** (does not call daemon `SwitchModel`). Everything else hits `on_receive_dispatch` → `internal_error("not implemented")` — that includes `authenticate`, `session/set_mode`, `session/set_config_option`, and the `session/cancel` notification (cancellation is instead approximated in-process: a second prompt answers the pending one with `StopReason::Cancelled` and increments `skip_response_done`).
19. Daemon→ACP mapping in `handle_session_message`/`daemon_msg_to_session_update`: `TextChunk→AgentMessageChunk`, `ThinkingChunk→AgentThoughtChunk`, `UserInputEcho→UserMessageChunk`, `ToolCall→SessionUpdate::ToolCall` (kind guessed from tool name), `ToolResult→ToolCallUpdate{Completed}` correlated by a single `last_tool_call_id` slot (diff segments become ACP `Diff` via `parse_unified_diff`), `ResponseDone→PromptResponse(EndTurn)`, `Error→` prompt error, title changes → `SessionInfoUpdate`. Infinity never sends ACP client-bound requests (`session/request_permission`, `fs/*`, `terminal/*`) — tools execute inside RAP servers, so ACP clients are pure observers/drivers.

### Boundaries

**Inputs/outputs of this slice.** In: `~/.infinity/{providers.json, rap.json, remotes.json, sessions.json}`, `{cwd}/.infinity/rap.json`; Unix-socket and WebSocket `ClientMessage` JSON; ACP JSON-RPC on stdio; RAP callbacks (HTTP POST `RapCallback`); provider NDJSON over Unix sockets. Out: `DaemonMessage` JSON; `RapInvocation` HTTP POSTs and lifecycle POSTs (`/close_thread`, `/cancel_tool_call`, `/migrate`, `/user_choice_response` answers); spawned provider and RAP-server OS processes; per-thread JSON state files. Downstream (other explorers): `infinity-agent-core` router/driver/completion loop consumes `InputMessage` + `ModelProvider` + per-thread `ThreadConfig`; the daemon only supplies `CatalogModelSource`, `SessionRapManager`, stores, and `DaemonObserver`.

**Seam 1 — local-model provider (llama.cpp/vLLM, OpenAI-compatible).** This is the cleanest seam; no daemon change is required. A provider binary must: (a) implement `ModelProvider::{list_models, invoke_model}` from [infinity-provider-protocol/src/lib.rs](../../../crates/infinity-provider-protocol/src/lib.rs:68); (b) expose it with `remote::serve_provider`, print the socket path as the first stdout line, log to stderr (pattern: [infinity-provider-bedrock/src/main.rs](../../../crates/infinity-provider-bedrock/src/main.rs:16)); (c) be registered as `{"local": {"command": ["infinity-provider-local", ...]}}` in `providers.json`, or installed via `infinity provider install local --crate <crate> [--git/--path]` (`install::run_provider_install`, grep-inspected). The daemon then spawns it at startup (`spawn_provider`), catalogs its models, and routes per-thread `ModelRef{provider_id:"local", model_id}` selections to it. Size estimate from evidence: the transport/main is ~35 lines; the substance is one request converter (`CompletionRequest` → OpenAI `chat/completions`: preamble→system message, `Message`/`ToolCall`/`ToolResult`/image mapping, `ToolDefinition`→`tools`) and one SSE→`StreamChunk` adapter that accumulates streamed tool-call argument fragments into `StreamChunk::ToolCall` and emits `Final{usage}` — comparable to Bedrock's convert+stream (~690 lines combined, likely less for OpenAI format). Shortcut: `infinity-provider-rig`'s `RigCompletionModel` + existing `convert.rs` reduce a rig-backed provider to model construction + `ModelEntry` + `serve_provider` main (tens of lines) *if* rig's OpenAI client is pointed at the local base URL — I could not verify rig's base-URL API from this tree (rig source not vendored; workspace pins `rig-core 0.31, default-features=false`, so a new crate would also need the right rig features). Gotchas: core always sends `max_tokens: None, additional_params: None`, so defaults must come from `ModelEntry.max_output_tokens`/provider config; `context_window` drives compaction, so it must be honest; set `supports_image_input=false` unless the local model is multimodal; classify local-server errors (`ErrorClass::ContextOverflow` on context-length errors is load-bearing); the model must actually do OpenAI-style tool calling, since every request carries the full RAP/built-in tool list. In-process alternative: `SessionManager::with_providers` accepts `Arc<dyn ModelProvider>` directly, but production `SessionManager::new` only spawns processes.

**Seam 2 — external CLI coding agents as supervised peers.** Two grounded routes. (a) *ACP client*: the dependency already ships both roles — crates.io `agent-client-protocol 0.11.1` (inspected under `~/.cargo/registry/src/.../agent-client-protocol-0.11.1/src/`) defines `role::acp::Client` with `Counterpart = Agent`, `Client.builder().connect_with(transport, ...)` in `lib.rs`, and client-sendable requests `initialize`, `session/new|load|list|prompt|set_model|set_mode|set_config_option`, `authenticate`, notification `session/cancel`, plus agent→client requests a host must answer (`session/request_permission`, `fs/read_text_file`, `fs/write_text_file`, `terminal/*`). Infinity uses none of this (`grep` finds no `Client::builder`/`send_request` in the workspace). Hosting Claude Code/Codex (when run in their ACP modes) would mean a new component that spawns the agent over stdio `ByteStreams` (the crate docs point at a separate `agent-client-protocol-tokio` spawn helper, not currently a dependency), drives `session/prompt`, translates `session/update` notifications onward, and makes policy decisions for permission/file/terminal requests — that policy surface is the real cost. (b) *RAP toolset wrapper*, which fits today's supervision best: model the external agent session as a command RAP server in `rap.json` (daemon already spawns, process-groups, restarts, and SIGINTs it via `ManagedRapServer`), following the sandbox streaming template — manifest tools such as `start_agent`/`send_to_agent`, an immediate `tool_result` with `subscription=true`, the agent's ongoing output as `subscription_event`s (`associative=true` to inline into the owning thread, or `false` to fan out to ephemeral handler subthreads), `user_choice` callbacks for permission prompts, `view_update` for a live transcript, `final=true` at exit, and `/cancel_tool_call` + `/close_thread` handlers to kill/clean up (templates: `handle_execute_command_streaming_inner`, `rap-github-event-poller`). Constraints from the evidence: all inbound events are anchored to one `(group_id, tool_call_id)` subscription owned by one thread; the daemon kills command servers when the session idles *unless* an active subscription keeps it "active"; external-URL (`toolset_server`) servers are never stopped by the daemon, which suits a separately supervised long-lived agent process. Note Infinity can already be *driven by* external ACP clients today (`infinity acp`); the reverse direction does not exist.

**Seam 3 — peer (agent-to-agent) messaging.** There is no peer mechanism today: `grep` for peer/A2A across crates finds nothing, and the only inter-thread tools are tree-shaped — `report_to_parent` (parent via `get_thread_parent_info`), `send_message_to_child` (explicitly rejects non-children), `close_thread` (self only) in [tools/thread.rs](../../../crates/infinity-agent-core/src/tools/thread.rs:644). But the transport for peers already exists: `ChannelSender::send_to_input_queue` accepts an `InputMessage` addressed to *any* `group_id`, `route_loop` will spawn/resume that thread's driver (admission only drops event-style input to unknown/stopped threads), and RAP callbacks prove external processes can already inject into arbitrary existing threads by `group_id`. A minimal peer tool could send `InputMessage::user_text(target_thread, ...)` today with no core change — but it would be indistinguishable from user input. A proper implementation needs: a new `TaggedSyntheticKind` variant (cf. `ThreadReport`/`ParentMessage` in [infinity-agent-core/src/message.rs](../../../crates/infinity-agent-core/src/message.rs:60)), handling in core's prepare path — which currently *drops* synthetic messages whose anchored `tool_call_id` can't be found in the recipient's history (`find_tool_call` else `PrepareResult::Handled`), the main friction for peer sends, since a peer has no spawn call in the target's history to anchor to — plus display mapping (`DaemonMessage::SubscriptionEvent` is the natural surface) and a decision on deferral (synthetics are deferred while a non-passive tool call is pending).

### Non-Obvious Things

- **Everything is single-threaded.** Daemon, CLI, agent system, drivers, and RAP-server management all live on one `current_thread` runtime + `LocalSet`; `SessionManager` is `Rc<Mutex<...>>` and driver futures are owned by the router's `FuturesUnordered`, not spawned tasks. Provider processes and RAP servers are separate OS processes mainly so their blocking/network work doesn't stall this loop — callbacks re-enter as queued `InputMessage`s.
- **Tool calls are fire-and-forget.** `Tool::execute` for RAP tools returns after the POST; the "result" is a future input message. A crashed RAP server that never calls back leaves the call pending until interrupted; only non-2xx and transport errors are synthesized into results by `invoke_rap_tool`.
- **No authentication on any local surface.** The callback listener, RAP invocation endpoints, WebSocket server, and Unix socket are unauthenticated (localhost trust). Sandbox-local even binds `0.0.0.0` ([sandbox-local/src/server.rs](../../../crates/sandbox-local/src/server.rs:25)). Anyone local who learns the callback URL and a thread ID can inject tool results/events into a live thread (router admission only checks existence/not-stopped). The RAP spec's security section acknowledges this is implementation-defined.
- **"Shutdown session" doesn't stop the agent system.** It flags the store and stops RAP servers; a mid-completion turn finishes, and user text revives everything. Likewise daemon shutdown needs no session teardown because state is written through to JSON files continuously.
- **Model/provider state is startup-frozen.** `list_models` runs once; provider processes are never restarted — a dead provider surfaces as per-request `Transient` errors from `RemoteModelProvider` until `infinity daemon restart`. `providers.json` order silently decides the default model.
- **ACP server quirks.** `session/new` creates nothing until the first prompt; `session/set_model` is a no-op stub; tool-result correlation assumes strictly sequential tool calls (single `last_tool_call_id`, `expect()` panics otherwise); session-ID mappings are persisted relative to the ACP server's cwd, not `~/.infinity`.
- **MCP is second-class by design here.** MCP servers are proxied into RAP with only two meta-tools (list/invoke), results are flattened to text, and MCP proxies are deliberately never shut down on idle because MCP lacks RAP's "state keyed by thread ID, restart is transparent" contract ([rap_servers.rs](../../../crates/infinity-daemon/src/rap_servers.rs:193)).
- **The daemon protocol doubles as the daemon-to-daemon protocol.** `Emigrate`/`ImportSession`/`BootRapServers` are ordinary `ClientMessage` variants; any process that can reach `daemon.sock` can request a full serialized session export.
- **Direct mode uses different state.** `--local`/fallback `run_direct` stores state under `./.infinity`, so its sessions are invisible to the `~/.infinity` daemon and vice versa.
- **Subscription identity is just the originating tool-call ID**, events have no sequence/ID of their own (dedup uses random UUIDs), and whether an event inlines or spawns a handler subthread is chosen by the *server* per event via `associative` — a powerful and easily misused knob for any future external-agent toolset.

### Open Questions

- Does rig 0.31's OpenAI client support a custom base URL usable for llama.cpp/vLLM, and which rig features must a new provider crate enable? Rig's source isn't in this tree and the workspace pins `rig-core` with `default-features = false`; I verified only the Infinity-side adapter (`RigCompletionModel`, `convert.rs`) and the docs' claims.
- How do real external agents (Claude Code, Codex, Pi) expose ACP — stdio spawn contract, protocol version, and which client-bound requests (permissions, fs, terminal) they actually send? I verified only what the `agent-client-protocol` crate can express, not any specific agent's behavior.
- Core internals I only sampled and other explorers own: `drive_thread`/`system/thread.rs` step loop, compaction, `HistoryManager`, and the remainder of `memory_store.rs` (persistence edge cases, `serialize_session` format) and `migrate.rs` (failure/rollback paths).
- Is there any backpressure or ordering guarantee between concurrent RAP callbacks, user input, and deferred synthetics beyond per-thread driver serialization? The channels are all unbounded `mpsc`; I found dedup but no ordering/rate controls in this slice.
- The WebSocket/web UI surface (`web_assets.rs`, `infinity-web`) and the Lambda/SQS deployment (`infinity-agent-lambda`, `sandbox-remote`) reuse these same protocol types, but I did not trace how faithfully they preserve subscription/deferral semantics (`NoDeferral` exists precisely because serverless differs).
